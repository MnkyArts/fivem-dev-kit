# FiveM Scripting Runtime & Server — Fact Sheet

A citations-backed reference on the FiveM scripting runtime (Lua/JS) and FXServer, compiled for an engineer writing a "write clean, performant, secure FiveM resources" guide. Every fact below cites an exact `path:line` from the local checkouts listed here — nothing is from memory.

Sources: `fivem` (CitizenFX/fivem) @ `0d8a2a6f7`, cited as `fivem/<path>:<line>`; `fivem-docs` (docs.fivem.net content) @ `e8113b6`, cited as `fivem-docs/<path>:<line>` (paths relative to `content/docs/`).

Compiled 2026-09-11. Facts marked `(inferred)` are reasonable deductions from the cited code/docs rather than explicit statements; facts marked `UNVERIFIED:` could not be confirmed in these checkouts and are flagged rather than invented.

## 1. Lua scheduler & threads

- `Wait`, `CreateThread`, `SetTimeout`, `ClearTimeout` are root-level Lua aliases of `Citizen.Wait`/`Citizen.CreateThread`/`Citizen.SetTimeout`/`Citizen.ClearTimeout`; the scheduling logic itself is implemented natively in the C++ script host, not in `scheduler.lua` — the Lua file only aliases the natives and builds events/exports/state-bags on top — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:112-115.
- A Lua coroutine that yields a number from `Wait(ms)` has that number read by the native host as a `wakeTime`; yielding `nil` (or a non-number) is treated as `wakeTime = 0` — Source: fivem/code/components/citizen-scripting-lua/src/LuaScriptRuntime.cpp:920-926.
- The host reschedules a waiting thread via `m_bookmarkHost->ScheduleBookmark(this, bookmark, -wakeTime)`, i.e. the coroutine's resume is registered as a "bookmark" with a deadline computed from the (negated) wake time, rather than being resumed immediately — Source: fivem/code/components/citizen-scripting-lua/src/LuaScriptRuntime.cpp:926; the `ScheduleBookmark` parameter is literally named `deadline` in the script-host IDL — Source: fivem/code/components/citizen-scripting-core/include/fxScripting.idl:189.
- Threads resume in deadline order (earliest scheduled wake time first) each time the host services bookmarks; a `Wait(0)` thread is bucketed to resume on the very next tick, not "no delay" — confirmed directly by the docs: "`Wait(0)` will pause the current coroutine until the next game tick." (inferred ordering mechanism from ScheduleBookmark's deadline semantics) — Source: fivem-docs/scripting-reference/runtimes/lua/functions/Citizen.Wait.md:75, fivem/code/components/citizen-scripting-lua/src/LuaScriptRuntime.cpp:920-926.
- The interval between ticks is frame-bound and non-deterministic — it is faster for players with higher FPS (docs give 60 fps ≈ 16.6 ms/tick, 180 fps ≈ 5.5 ms/tick as examples), so `Wait(N)` is a *minimum* delay in wall-clock terms, not an exact one — Source: fivem-docs/scripting-reference/runtimes/lua/functions/Citizen.Wait.md:79-85.
- `SetTimeout(ms, callback)` is a distinct native scheduling path from `Wait`, implemented via `ScheduleBookmarkSoon(bookmark, -timeout)` → `ScheduleBookmark(this, bookmark, timeout)`; it schedules `callback` to run once after `ms`, without requiring (or blocking) a coroutine the caller is already running in — Source: fivem/code/components/citizen-scripting-lua/src/LuaScriptRuntime.cpp:1099,1266-1277; fivem-docs/scripting-reference/runtimes/lua/functions/Citizen.SetTimeout.md:5-16.
- `CreateThread(handler)` runs `handler` as a new coroutine "asynchronously" relative to the caller — code after the `CreateThread(...)` call runs immediately without waiting for the new thread — Source: fivem-docs/scripting-reference/runtimes/lua/functions/Citizen.CreateThread.md:5,20-24.
- A thread body that never calls `Wait` (e.g. a `while true do ... end` with no `Wait`) will hang/crash the client, per an explicit doc warning — Source: fivem-docs/scripting-reference/runtimes/lua/functions/Citizen.Wait.md:49-51 (warning callout).
- `Citizen.CreateThreadNow` exists and is used internally (e.g. to run event handlers and ref calls immediately rather than queued for a later tick — see Section 2/3), but is undocumented by FiveM's own docs site (the doc page is a stub reading only "-- todo") — Source: fivem-docs/scripting-reference/runtimes/lua/functions/Citizen.CreateThreadNow.md:8-10; fivem/data/shared/citizen/scripting/lua/scheduler.lua:171-173.
- `SetInterval`/`ClearInterval` do **not** exist in the Lua runtime — `scheduler.lua` defines only `Wait`, `CreateThread`, `SetTimeout`, `ClearTimeout` as scheduling primitives, no interval variant — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:112-115 (absence, cross-checked against the full file read). (The JS runtime *does* have `setInterval`/`clearInterval` — see Section 13, out of scope here.)
- `Citizen.Await(promise)` asserts it is running inside a coroutine; calling it from a non-scheduler context (e.g. top-level resource init code, outside `CreateThread`/`SetTimeout`/an event handler) throws immediately with the message *"Current execution context is not in the scheduler, you should use CreateThread / SetTimeout or Event system (AddEventHandler) to be able to Await"* — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:85-87.
- `Citizen.Await` mechanics: if the promise is still pending (`state == 0`), it yields a special `AwaitSentinel` value, attaches a resume callback via `promise:next(reattach, reattach)`, then yields again until the host reattaches it; once settled, a promise in state `2` (REJECTING) or `4` (REJECTED) makes `Await` raise a Lua `error(promise.value, 2)`, otherwise it returns `promise.value` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:85-100.
- Promise states (from the bundled zserge/lua-promises implementation `promise.new()`) are `PENDING=0`, `RESOLVING=1`, `REJECTING=2`, `RESOLVED=3`, `REJECTED=4` — Source: fivem/data/shared/citizen/scripting/lua/deferred.lua:11-15.
- Errors thrown inside a scripted thread are formatted via a native `FORMAT_STACK_TRACE` call and printed as `^1SCRIPT ERROR: <message>^7\n<stacktrace>`; this happens through an `xpcall(fn, doStackFormat)` boundary around ref calls and event-handler dispatch, so one erroring handler/thread does not corrupt the host's C stack — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:44-46,454-463,482-485.
- Calling a global that resolves to no known native and no user-defined value does not raise an error at the point of reference — the `_G` metatable's `__index` looks it up via `Citizen.LoadNative`, and on failure caches the miss in a local `nilCache` table and returns `nil` silently; the error only surfaces later, when Lua tries to *call* that `nil` value — Source: fivem/data/shared/citizen/scripting/lua/natives_loader.lua:74-98.

## 2. Events (Lua + JS)

- `AddEventHandler(eventName, handler)` stores `handler` in a per-event-name list and calls the native `RegisterResourceAsEventHandler(eventName)` so the resource's script runtime receives dispatch for that event; it returns a `{key, name}` table usable with `RemoveEventHandler` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:255-277.
- `RegisterResourceAsEventHandler` is described as "An internal function which allows the current resource's HLL script runtimes to receive state for the specified event"; passing `"*"` as the event name disables HLL event filtering entirely for the resource — Source: fivem/ext/native-decls/RegisterResourceAsEventHandler.md:11-14.
- An event is only triggerable **from the network** (i.e. accepted when its `source` starts with `"net"`) if it was registered "safe for net" — this is exactly what `RegisterNetEvent(eventName)` sets (`tableEntry.safeForNet = true`); an `AddEventHandler`-only registration is not network-triggerable — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:292-303; if a net-sourced event arrives for a handler that isn't marked safe, the Lua runtime traces `"event " .. eventName .. " was not safe for net"` and drops it without invoking any handler — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:138-144.
- `RegisterNetEvent(eventName[, callback])` supports a two-argument form: if `callback` is provided, it is registered via `AddEventHandler` in the same call, equivalent to calling `RegisterNetEvent` then `AddEventHandler` separately — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:292-308; fivem-docs/scripting-reference/runtimes/lua/functions/RegisterNetEvent.md:7-8,13-39. On the server, `RegisterServerEvent` is a plain alias of `RegisterNetEvent` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:331.
- One internal event name, `__cfx_internal:commandFallback`, is exempt from being marked `safeForNet` even when passed to `RegisterNetEvent` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:288-293,302-303.
- Event dispatch (native → Lua) sets a per-invocation `source` global (`_G.source`), saves and restores the *previous* value around the call (`local lastSource = _G.source` ... `_G.source = lastSource` at the end) — so nested `TriggerEvent` calls correctly restore the outer handler's `source` once the inner dispatch finishes — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:125-129,179.
- Each registered handler for a firing event is invoked in its own `Citizen.CreateThreadNow(...)` coroutine (started immediately, not queued for a later tick); if multiple handlers are registered for the same event name, each gets an independent coroutine, so one handler's internal `Wait` does not block the others from starting — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:160-175.
- `TriggerEvent(eventName, ...)` msgpack-packs the varargs and calls the native `TriggerEventInternal` inside a stack-boundary wrapper; because dispatch runs handlers via `CreateThreadNow`, a handler executes synchronously up to its first `Wait`/`Await`, i.e. `TriggerEvent` is effectively synchronous for handlers that never yield — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:310-316,171-173 (inferred synchronicity from CreateThreadNow semantics). Consistent with this, the docs state `TriggerEvent()` returns `true` if the event was canceled by a handler, meaning the call has already run the handler(s) by the time it returns — Source: fivem-docs/scripting-manual/working-with-events/canceling-events.md:52-59.
- `TriggerServerEvent(eventName, ...)` (client-only) and `TriggerClientEvent(eventName, playerId, ...)` / `TriggerLatentClientEvent(eventName, playerId, bps, ...)` (server-only) all msgpack-pack their varargs and call the matching `...Internal` native; `TriggerClientEvent`'s `playerId` of `-1` broadcasts to all clients (inferred from the native's use as a "target" and common FiveM convention; not restated verbatim in the read doc stub) — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:318-329,411-422; fivem/ext/native-decls/TriggerClientEventInternal.md:8; fivem/ext/native-decls/TriggerLatentClientEventInternal.md:8 (both `apiset: server`).
- `TriggerLatentClientEvent`'s extra `bps` argument throttles delivery of that specific event's payload to at most `bps` bytes per second (rate-limited/latent delivery) rather than sending it in one reliable burst — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:325-329; fivem/ext/native-decls/TriggerLatentClientEventInternal.md:8,14-18 (parameter present; exact throttling algorithm not documented in the stub — UNVERIFIED beyond "bytes per second" naming).
- Event payloads are serialized with `msgpack_pack_args`/`msgpack_unpack`; only over-the-wire-representable types survive a network trip — plain tables, strings, numbers, booleans round-trip normally, while function values are transparently replaced by function-reference proxies (see Section 3) via custom msgpack ext types `EXT_FUNCREF`/`EXT_LOCALFUNCREF` (10/11), and `Entity`/`Player` handles use their own ext types 41/42 that pack down to a network id / server id string — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:537-624,813-943.
- `CancelEvent()` cancels the currently executing event but "does not stop other event handlers from running" — every registered handler still executes — Source: fivem/ext/native-decls/CancelEvent.md:8-11; fivem-docs/scripting-manual/working-with-events/canceling-events.md:9.
- `WasEventCanceled()` returns whether the last *locally* triggered event was canceled; the docs explicitly note it "only works for local events" (not for events received over the network) — Source: fivem/ext/native-decls/WasEventCanceled.md:8-14; fivem-docs/scripting-manual/working-with-events/canceling-events.md:40.
- `RemoveEventHandler(eventData)` requires the `{key, name}` table returned by `AddEventHandler`; passing anything else (missing `.key`/`.name`) raises `'Invalid event data passed to RemoveEventHandler()'` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:279-286.
- JS: `on(eventName, callback)` (= `addEventListener`) takes an optional third `netSafe` boolean parameter (default `false`); `onNet(eventName, callback)` is sugar for `addEventListener(eventName, callback, true)`. Both always call the native `RegisterResourceAsEventHandler(eventName)` regardless of `netSafe` — Source: fivem/data/shared/citizen/scripting/v8/main.js:243-259.
- JS's `RegisterNetEvent(name)` is **not** the same shape as Lua's: it takes no handler argument and does not call `AddEventHandler` — it only adds `name` to the internal `netSafeEventNames` set and returns nothing (`void`); use `onNet`, or `on` + `RegisterNetEvent`, to both mark-safe and listen — Source: fivem/data/shared/citizen/scripting/v8/main.js:265.
- JS event dispatch (`Citizen.setEventFunction`) runs **raw** listeners (`addRawEventListener`) unconditionally first (even if the payload fails to decode as an array), then normal listeners; if a normal listener's return value is a `Promise`, it is awaited asynchronously and a rejection is caught and logged as `'Unhandled promise failure:'` rather than crashing the dispatcher; each listener is individually wrapped in `try/catch`, so one throwing listener does not stop the others — Source: fivem/data/shared/citizen/scripting/v8/main.js:484-537.
- Unlike the Lua runtime, the JS dispatcher does **not** save/restore a prior `global.source` around nested dispatch — it unconditionally sets `global.source = null` at the end of every `setEventFunction` invocation (compare Lua's `lastSource` save/restore) — Source: fivem/data/shared/citizen/scripting/v8/main.js:486,539 vs fivem/data/shared/citizen/scripting/lua/scheduler.lua:127-129,179.
- JS's net-unsafe-event message differs slightly in wording/case from Lua's: JS logs `` `Event ${name} was not safe for net` `` via `console.error`, Lua traces `'event ' .. eventName .. " was not safe for net"` via `Citizen.Trace` — both drop the event without running handlers — Source: fivem/data/shared/citizen/scripting/v8/main.js:488-494 vs fivem/data/shared/citizen/scripting/lua/scheduler.lua:138-144.
- JS `emit`/`TriggerEvent` and (server) `emitNet`/`TriggerClientEvent`(+`TriggerLatentClientEvent`) / (client) `emitNet`/`TriggerServerEvent`(+`TriggerLatentServerEvent`) mirror the Lua natives 1:1, packing args with the runtime's msgpack codec before calling the same `...Internal` natives — Source: fivem/data/shared/citizen/scripting/v8/main.js:270-293,329-341; fivem/data/shared/citizen/scripting/v8/index.d.ts:96-101,109-111.
- `global.source` (JS) / `source` (Lua) is exposed as a plain global variable, typed `declare var source: number` in the TS defs — Source: fivem/data/shared/citizen/scripting/v8/index.d.ts:142.

## 3. Exports & callbacks

- The `exports` table is built with a metatable: indexing `exports.<resource>` returns a proxy whose own `__index` (i.e. accessing `.<fnName>`) does the real work of resolving that resource's export — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:689-726.
- Under the hood, an export is exposed as an event named `` `__cfx_export_<resource>_<exportName>` ``, with one hardcoded special case: if `resource == "txAdmin"`, the resource is silently remapped to `"monitor"` for the purposes of that event name, in **both** the Lua and JS runtimes — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:627-631; fivem/data/shared/citizen/scripting/v8/main.js:548-552.
- Calling `exports.<resource>:<fnName>(...)` the first time triggers `TriggerEvent('__cfx_export_<resource>_<fnName>', function(exportData) ... end)` to fetch the underlying function and caches it in a per-resource table (`exportsCallbackCache`); subsequent calls reuse the cached function directly (cheap `pcall`), so only the first call per (resource, exportName) pays for the cross-resource event round-trip — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:634-635,703-719; fivem/data/shared/citizen/scripting/v8/main.js:544,583-599 (mirrors the same cache-on-first-use pattern).
- The export cache for an exporting resource is cleared when that resource stops (`AddEventHandler('on{Server,Client}ResourceStop', function(resource) exportsCallbackCache[resource] = {} end)`), so callers automatically re-resolve (and will error if the resource hasn't restarted yet) after a restart — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:656-663; fivem/data/shared/citizen/scripting/v8/main.js:571-573.
- Calling a non-existent export raises a Lua error immediately: `'No such export ' .. k2 .. ' in resource ' .. resource` — it does not return `nil` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:707-714. JS's equivalent throws `` `No such export ${k} in resource ${resource}` `` from the `Proxy` `get` trap — Source: fivem/data/shared/citizen/scripting/v8/main.js:587-594.
- Two ways to publish an export in Lua: (a) declare the name in the fxmanifest's `exports {}`/`server_exports {}` list *and* define a same-named global function — a startup loop reads the resource's own declared export names via `GetNumResourceMetadata`/`GetResourceMetadata` (key `"export"` client-side, `"server_export"` server-side) and auto-registers a responder returning `_G[exportName]`; or (b) call `exports('name', fn)` directly, which registers its own responder unconditionally via the `exports` table's `__call` metamethod — the two are independent; explicit `exports('name', fn)` works even if `name` was never declared in the manifest — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:637-654,732-736.
- Errors thrown inside an export function are caught with `pcall` and re-raised in the caller with a formatted message including the export/resource name, with very long error output truncated to the first/last 1024 characters (total budget 2048) — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:677-686. JS instead swallows the original error and re-throws a generic `` `An error occurred while calling export ${k} of resource ${resource} - see above for details` `` (the original error object/message is not included in the thrown JS error) — Source: fivem/data/shared/citizen/scripting/v8/main.js:597-603.
- JS's `exports('name', fn)` call form (the Proxy `apply` trap) strictly requires exactly two arguments and throws `'this needs 2 arguments'` otherwise; Lua's equivalent `__call` metamethod performs no such arity check — Source: fivem/data/shared/citizen/scripting/v8/main.js:612-622 vs fivem/data/shared/citizen/scripting/lua/scheduler.lua:732-736.
- Assigning to an export (`exports.foo = ...`) or to the `exports` table itself always errors in both runtimes ("cannot set values on an export resource" / "cannot set values on exports") — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:722-730; fivem/data/shared/citizen/scripting/v8/main.js:606-609,624-626.
- `Citizen.GetFunctionReference(func)` registers `func` in a local `funcRefs` table (refcount starts at 0) and returns an opaque ref string from the native `Citizen.CanonicalizeRef`; passing something that's already a funcref proxy table wraps it in a new closure rather than erroring; passing a non-function, non-funcref value returns `nil` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:425-452.
- Invoking a function reference (calling the value returned by `GetFunctionReference`) goes through the `funcref_mt.__call` metamethod: packs args, calls native `Citizen.InvokeFunctionReference` inside a boundary wrapper, and unpacks the result — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:557-565.
- On the receiving side, `Citizen.SetCallRefRoutine` runs the referenced function inside `Citizen.CreateThreadNow` wrapped in `xpcall(..., doStackFormat)`; if the call did not finish synchronously (the referenced function itself `Wait`ed), the routine returns a special `{__cfx_async_retval = <setter fn>}` payload instead of real return values, and the caller side (if currently running inside a coroutine) wraps that into a promise and `Citizen.Await`s it transparently — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:465-511,568-581.
- Function references are reference-counted: `Citizen.SetDuplicateRefRoutine`/`SetDeleteRefRoutine` increment/decrement a `.refs` counter and the entry is dropped from `funcRefs` once `refs <= 0`; the funcref proxy's `__gc` metamethod also calls the native `DeleteFunctionReference` when the Lua-side handle is collected — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:513-535,544-547.
- Cost: each function-reference call crosses the msgpack (de)serialization boundary and a native invoke (`Citizen.InvokeFunctionReference`/`Citizen_InvokeFunctionReference`) even for calls back into the *same* resource — it is not a cheap direct Lua call — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:557-565 (inferred cost characterization from the serialize+native-call path).
- JS mirrors this with `Citizen.makeRefFunction`/`getRefFunction` (caller-visible ref creation) and `setCallRefFunction` (callee-side invocation, wraps a `Promise`-returning callback the same way as Lua's "waited" case) — Source: fivem/data/shared/citizen/scripting/v8/main.js:61-90,159-228.

## 4. State bags

- `GlobalState`, `Entity(e).state`, `Player(id).state`, and `LocalPlayer.state` are all backed by one local factory, `NewStateBag(bagId)`, which returns a table wrapped in `__index`/`__newindex` metamethods — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:818-836
- `GlobalState` is simply `NewStateBag('global')` — the bag id is the fixed literal string `"global"` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:838
- Reading `state.key` goes through `__index` and calls the `GetStateBagValue(bagId, key)` native; a bare-assignment write `state.key = v` goes through `__newindex` and calls `SetStateBagValue(bagId, key, payload, len, replicated)` with `replicated` hardcoded to the value of `isDuplicityVersion` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:820,828,831-834
- `isDuplicityVersion` is a scheduler.lua-local set once from the `IsDuplicityVersion()` native (true when running as the server runtime, false on the client) — this is the exact mechanism behind "state set from the server is replicated by default, state set from clients is not" (docs restate the same rule) — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:28; fivem-docs/scripting-manual/networking/state-bags.md:69
- `state:set(key, value, replicated)` is the explicit override: `__index` special-cases the literal key `'set'` and returns a closure calling `SetStateBagValue(bagId, key, payload, len, replicated)` with an explicit boolean instead of the `isDuplicityVersion` default — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:821-825
- State values are msgpack-packed via `msgpack_pack` before `SetStateBagValue`, and implicitly unpacked on the native return from `GetStateBagValue` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:823-824,828
- Assigning an arbitrary field directly on an `Entity(e)` or `Player(id)` wrapper (i.e. NOT through `.state`) throws `"Setting values on Entity is not supported at this time."` / `"...Player..."` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:865-867,904-906
- Entity state-bag id resolution: if the entity is networked (always true server-side; client-side only if `NetworkGetEntityIsNetworked` is true) the id is `entity:<networkId>`; otherwise (client-only, non-networked local entity) the id is `localEntity:<entityHandle>` and `EnsureEntityStateBag(entityGuid)` is called first to create it — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:840-847
- On the server specifically, every `Entity(e).state` property access additionally calls `EnsureEntityStateBag(e)` again before returning the bag wrapper, so the bag is guaranteed to exist by the time you read/write it — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:855-857
- Player state-bag id is always `player:<serverId>`; `LocalPlayer.state` resolves `serverId` via `GetPlayerServerId(PlayerId())` since `LocalPlayer`'s internal handle is the sentinel `-1` — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:888-896
- The `LocalPlayer` global (`= Player(-1)`) is defined only `if not isDuplicityVersion` — it does not exist in server scripts at all (not even as nil-with-metatable; the name is simply never assigned) — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:945-946
- `Entity`/`Player` wrapper tables are msgpack-extended with custom `__pack`/`__unpack`: an `Entity` serializes as its network-id string (`NetworkGetNetworkIdFromEntity`) and rehydrates via `NetworkGetEntityFromNetworkId`; a `Player` serializes as its numeric id and rehydrates via `tonumber` — so entity/player references (not just their raw handles) survive as event/export arguments across the msgpack boundary — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:869-884,908-923
- Server registers the global bag explicitly at startup: `m_globalBag = sbac->RegisterStateBag("global", true)` (the `true` is `useParentTargets`) — Source: fivem/code/components/citizen-server-impl/src/state/ServerGameState.cpp:4584
- Underlying C++ `StateBag::SetKey(source, key, data, replicated = true)` is the single choke point every state write goes through; `StateBagComponent::RegisterStateBag(id, useParentTargets = false)` creates a bag on demand — Source: fivem/code/components/citizen-resources-core/include/StateBagComponent.h:88,155
- `AddStateBagChangeHandler(keyFilter, bagFilter, handler)` — native `ADD_STATE_BAG_CHANGE_HANDLER`; handler signature is `function(bagName, key, value, reserved, replicated)` where `reserved` is documented as currently unused, and a change handler **cannot** reject/veto the change (fire-only, not a gate) — Source: fivem/ext/native-decls/AddStateBagChangeHandler.md:8,13-26
- Confirmed bag-name formats from the native docs: `player:<Source>`, `entity:<NetID>`, and `localEntity:<Handle>` (the doc explicitly lists all three, correcting a common assumption that only `entity:`/`player:`/`global` exist) — Source: fivem/ext/native-decls/AddStateBagChangeHandler.md:19-20

## 8. Resource manifest

**Manifest file & parsing**

- The manifest is a Lua file named `fxmanifest.lua` (preferred) or, legacy, `__resource.lua`, run in its own throwaway Lua state separate from the resource's actual scripts — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:8, fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:155-166.
- The loader tries `fxmanifest.lua` first, then falls back to `__resource.lua` only if the first doesn't exist — they are not merged, exactly one is used — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:231,238.
- The manifest Lua state only opens `base`, `table`, `string`, `math`, `debug`, `coroutine`, `utf8` and a `json` (rapidjson) library — `io` and `os` are deliberately excluded ("luaL_openlibs version without io/os libs") — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:19-30.
- Before running the resource's own manifest file, the loader first runs `citizen:/scripting/resource_init.lua` (i.e. `fivem/data/shared/citizen/scripting/resource_init.lua` — note: not under the `lua/` subdirectory) in the same state — this is what defines the `fx_version`, `client_script`, `server_script`, `exports`, etc. DSL functions that call the injected `AddMetaData` global — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:220.
- After `resource_init.lua` runs (and before the resource's own manifest file runs), the globals `dofile`, `load` and `loadfile` are explicitly nilled out of the manifest Lua state — manifests cannot load or execute arbitrary code/files — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:222-229.
- Every `key, value` pair a manifest declares becomes a metadata entry via an injected `AddMetaData(key, value)` closure, which also records the declaring file + line for diagnostics — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:177-211.
- A resource can define arbitrary custom metadata keys beyond the built-in ones (e.g. `my_data 'one'`), readable at runtime via `GET_NUM_RESOURCE_METADATA`/`GET_RESOURCE_METADATA` natives — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:30-38.
- Entry types that support glob patterns (`*.lua` non-recursive, `**/*.lua` or `**.lua` recursive, `**/cl_*.lua` recursive+prefix) are documented per-key; `client_script`/`server_script`/`shared_script`/`data_file` all support globbing — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:43-53,82,94,100,192.

**`is_cfxv2` — the flag that actually matters for native-call performance, and it is NOT `fx_version`**

- When (and only when) a resource's manifest filename is `fxmanifest.lua` (not the legacy `__resource.lua`) and it parsed successfully, the loader auto-injects a metadata key `is_cfxv2 = "true"` — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:266-269.
- A resource's own manifest cannot set this key itself: the `AddMetaData` closure explicitly ignores (case-insensitively) any user-supplied key literally named `is_cfxv2` — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:184-185,207.
- At native-call time, the Lua native loader first checks `is_cfxv2`; only if that is true does it then check the manifest key `use_experimental_fxv2_oal` to decide whether to use the fast in-process native call path (`Lua_GetNative`) instead of the legacy per-native-hash file loader (`OpenSystemFile("...0x%08x.lua")`) — Source: fivem/code/components/citizen-scripting-lua/src/LuaScriptNatives.cpp:396-411.
- A code comment marks this as temporary/off-by-default: `// TODO/TEMPORARY: fxv2 oal is disabled by default for now`, and a `#if !defined(GTA_FIVE) || (LUA_VERSION_NUM == 504)` guard around the OAL branch is currently commented out (i.e. not actually restricting OAL to non-GTA5 games or Lua 5.4 at present) (inferred: the restriction is dormant/unenforced in this build) — Source: fivem/code/components/citizen-scripting-lua/src/LuaScriptNatives.cpp:398,406-410.

**`fx_version` matrix — verified against both the docs and the 3 engine call sites; do not assume newer tiers imply Lua-version changes, they don't**

- `fx_version` is a string tier name from an ordered list; each tier inherits all effects of every tier before it — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:62,426; fivem/code/components/citizen-resources-core/include/ManifestVersionsV2.h:1-2.
- The only three FXv2 tier names that exist in this checkout are, in order, `adamant`, `bodacious`, `cerulean` — Source: fivem/code/components/citizen-resources-core/include/ManifestVersionsV2.h:8,13,17.
- `adamant` (dated 2020-02 in `IsManifestVersionV2Between` gates — but docs say 2019-12): requires a `game` key to be specified at all (mandatory for RedM); is the FXv2 equivalent of legacy FXv1 GUID `44febabe-d386-4d18-afbe-5e627f4af937` — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:437-440.
- `adamant`+ also makes the Lua client runtime load a universal, non-build-pinned native table (`natives_universal.lua` / `rdr3_universal.lua` / `ny_universal.lua` depending on target game, or `natives_server.lua` if none of those build defines apply) instead of the specific-GTA-build-pinned `natives_21e43a33.lua` default — Source: fivem/code/components/citizen-scripting-lua/src/LuaScriptRuntime.cpp:1326,1340-1357.
- Server-side, a resource that is below `adamant` (no recognized `fx_version`) is refused at mount/start time: `ServerResources.cpp` prints `"Resource %s does not specify an `fx_version` in fxmanifest.lua."` and sets `allowed = false`, i.e. the resource will not start — Source: fivem/code/components/citizen-server-impl/src/ServerResources.cpp:536-540.
- Server-side resource scanning separately flags any resource that is below BOTH `adamant` (FXv2) and the last FXv1 GUID `44febabe-...` AND still has `client_script` entries as `"outdated_manifest"` — Source: fivem/code/components/citizen-server-impl/src/ServerResourceList.cpp:286-304.
- `bodacious`: implies `clr_disable_task_scheduler` is set for the resource (server C# library compatibility); JS runtime does **not** alias `window` to the global object at/after this tier (pre-bodacious resources get `window === global` for compat) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:432-435; fivem/code/components/citizen-scripting-v8/src/V8ScriptRuntime.cpp:1834-1843 (the code checks `!isGreater`, i.e. only aliases `window` when the resource is *below* bodacious).
- `cerulean`: NUI resources load in a browser "secure context" (enables WASM/fetch APIs), which requires NUI callback fetches to target `https://cfx-nui-<resource>/...` instead of the legacy `http://<resource>/...`/`nui://` scheme — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:428-430; fivem/code/components/nui-resources/src/ResourceUI.cpp:71-72 (chooses URL prefix `"https://cfx-nui-"` vs `"nui://"` based on this exact check).
- **Verified false assumption to flag explicitly**: `cerulean` does **not** default `lua54` to yes and has nothing to do with the Lua interpreter version — no code path in `citizen-scripting-lua` reads a `"lua54"` resource-metadata key at all (searched case-insensitively across the whole component tree) — Source: fivem/code/components/citizen-scripting-lua/ (absence, searched via `rg -i lua54`, no metadata-key read found), corroborated by fivem-docs/scripting-reference/resource-manifest/_index.md:299-305.

**`lua54 'yes'` — resolved: it's a dead/no-op flag, not a live gate**

- The docs explicitly say `lua54` is deprecated and "you do not need to enable it": as of June 2025, Lua 5.3 support was removed entirely and *all* Lua scripts now run on 5.4 regardless of this key — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:299-305.
- This matches the engine: there is no remaining Lua 5.3 build variant in this checkout (`rg -i lua53` across `code/components` and `code/tests` returns nothing), and the sole Lua component's build comment says its defines "carryover from lua54.lua", i.e. only one (5.4) Lua build config exists — Source: fivem/code/components/citizen-scripting-lua/component.lua:1; fivem/code/tests/server/TestLua.cpp:52 ("tests have to use lua54 because it gets linked second so the LuaScriptRuntime is for lua54") (inferred: confirms only a single, 5.4-only Lua runtime is compiled).
- Practical implication for the guide: setting or omitting `lua54 'yes'` has no runtime effect in current FXServer builds; it's safe to omit, and safe to leave in old resources without changing behavior (inferred) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:299-305.

**Other manifest keys (semantics, from the docs page, the canonical reference)**

- `game`: declares supported game API set(s); values `common` (game-agnostic, CitizenFX APIs only), `gta5`, `rdr3`; a resource must declare exactly one matching category — declaring both `common` and a specific game, or matching neither, is treated as "ill-formed" and the resource is refused (`allowed = false`) at start — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:64-72; fivem/code/components/citizen-server-impl/src/ServerResources.cpp:522-534.
- `client_script`/`server_script`/`shared_script`: load a file on client/server/both respectively; file extension picks the loader — `.lua` → Lua, `.net.dll` → Mono/.NET (`CitizenFX.Core.Client`/`.Server`), `.js` → V8 (client_script only, per the docs table) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:84-96.
- `export`/`server_export`: declares a global function name to be exported from a client/server script respectively (the docs note the `exports('name', fn)`/`Exports.Add` runtime API is preferred over the static manifest form) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:104-151.
- `ui_page`: sets the resource's NUI page (a bundled `file` or an absolute URL) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:153-165.
- `loadscreen`: sets the HTML file used as the game loading screen (also must be listed via `file`); `loadscreen_manual_shutdown 'yes'` stops the loading-screen NUI auto-closing, requiring an explicit `SHUTDOWN_LOADING_SCREEN_NUI` native call — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:224-240.
- `file`: adds a file to the resource's download packfile so clients fetch it — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:242-248.
- `data_file 'TYPE' 'path'`: registers a file (already added via `file`/`files`, supports globbing in the filename) with the game's extra-content data-file system (e.g. `AUDIO_WAVEPACK`, `VEHICLE_METADATA_FILE`, `HANDLING_FILE`) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:190-206.
- `this_is_a_map 'yes'`: marks the resource as a GTA map and reloads map storage on load — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:208-214.
- `server_only 'yes'`: marks the resource server-only; clients never download any of its files — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:216-222.
- `dependency`/`dependencies`: requires another resource to load first; the same field also accepts runtime-constraint strings: `/server:<build>` (min server build), `/policy:<name>` (server key policy grant, e.g. `subdir_file_mapping`), `/onesync` (state awareness must be on), `/gameBuild:<code>` (min game build, same value space as `sv_enforceGameBuild`), `/native:<hash>` (a specific server native must be supported) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:250-285.
- `provide`: marks this resource as a drop-in replacement for another named resource — if something depends on the provided name, this resource starts instead — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:323-329.
- `escrow_ignore`: lists files to exclude from Asset Escrow protection — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:288-297.
- `node_version '22'`: selects the server JS (Node.js) runtime version; default is `16`, the only other currently documented option is `22` — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:311-321.
- `use_experimental_fxv2_oal 'yes'`: opts a Lua resource into OAL ("One Argument List") native calls for corrected return types and faster calls; explicitly experimental; **breaks `vector3` auto-unpacking** — arguments like `SetEntityCoords(ped, coords)` must be manually unpacked to `SetEntityCoords(ped, coords.x, coords.y, coords.z)` under OAL; also breaks unpredictably for undocumented/mistyped natives because OAL blindly converts to the underlying declared type — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:331-358.
- `clr_disable_task_scheduler 'yes'`: disables the server's custom C# TPL task scheduler for better third-party .NET library compatibility, at the cost of needing an explicit `await Delay(0);` to return to the main thread; implied automatically once `fx_version` is `bodacious` or later — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:360-368.
- `convar_category 'Name' { "Group title", { {label, convar_name, type, default, ...}, ... } }`: surfaces convars in FxDK's Project Settings UI; types are `CV_STRING`, `CV_BOOL`, `CV_INT`, `CV_SLIDER`, `CV_COMBI`, `CV_PASSWORD`, `CV_MULTI`; prefix the convar name with `$` if it's replicated (`setr`) or `#` if it's server-info (`sets`) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:370-420.
- `before_level_meta`/`after_level_meta`/`replace_level_meta`: inject or replace GTA level-meta content; documented as deprecated in favor of `data_file` — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:167-188.
- Legacy `resource_manifest_version` (GUID-based, FXv1) still exists but is deprecated in favor of `fx_version`; FXv1's last meaningful GUID tier `44febabe-d386-4d18-afbe-5e627f4af937` (2017-06-07) switched client Lua to `natives_universal.lua` and made scripts register as game-network scripts (required for entity networking), also changing `CREATE_VEHICLE`-family behavior when passing `true, true` network flags — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:74-78,442-471.
- `games` (plural, e.g. `games {'gta5','rdr3'}`) is documented on this page only via the singular `game` directive repeated — the docs page and the parsed-example both show `game` used multiple times for multi-game resources, not a distinct `games` key (inferred from the worked example) — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:22-23.
- `@resource/file.lua`-style cross-resource includes are a Lua `require`/loader path convention handled by the script host's file resolution, not a manifest key — UNVERIFIED as a manifest-level concept: not documented on this manifest reference page — Source: fivem-docs/scripting-reference/resource-manifest/_index.md (absence on this page).

## 9. Core events reference

General conventions:

- Resource lifecycle events pass a single `resourceName` string argument — no `source`. — Source: fivem-docs/scripting-reference/events/list/onResourceStart.md:11, fivem-docs/scripting-reference/events/list/onResourceStop.md:11, fivem-docs/scripting-reference/events/list/onClientResourceStart.md:11, fivem-docs/scripting-reference/events/list/onClientResourceStop.md:11
- OneSync "parsed game event" natives (weaponDamageEvent, explosionEvent, ptFxEvent, startProjectileEvent, giveWeaponEvent, removeWeaponEvent, removeAllWeaponsEvent) all follow a `(sender: number, data: {...})` signature, where `sender` is the triggering player's server id and `data` is a msgpack map of event-specific fields — Source: fivem/code/components/citizen-server-impl/src/state/ServerGameState.cpp:4934 (weaponDamageEvent declare), fivem/code/components/citizen-server-impl/src/state/ServerGameState.cpp:5491 (removeAllWeaponsEvent declare), fivem/code/components/citizen-server-impl/src/state/ServerGameState.cpp:5519 (startProjectileEvent declare), fivem/code/components/citizen-server-impl/src/state/ServerGameState.cpp:5678 (ptFxEvent declare)
- These game events are dispatched server-side via `ResourceEventManagerComponent::TriggerEvent2`/`QueueEvent2`, which msgpack-pack the argument list and call the named Lua/JS event — Source: fivem/code/components/citizen-resources-core/include/ResourceEventComponent.h:148, fivem/code/components/citizen-resources-core/include/ResourceEventComponent.h:164
- `TriggerEvent2` returns `bool` (false when the event was canceled) and the call site can branch on that return value to abort the underlying action; `QueueEvent2` returns `void` — it enqueues the event and cannot report back whether a handler canceled it — Source: fivem/code/components/citizen-resources-core/include/ResourceEventComponent.h:148, fivem/code/components/citizen-resources-core/include/ResourceEventComponent.h:164

### Entity lifecycle (OneSync)

- `entityCreating(handle: number)` — server-side, fired while an entity is being created; **the doc comment explicitly states this event "can be canceled to instantly delete the entity"** — Source: fivem/code/components/citizen-server-impl/src/state/ServerGameState.cpp:3660-3670

## 10. Commands, ACE & key mappings

- `RegisterCommand(commandName, handler, restricted)` is `apiset: shared` (works client or server); signature `void REGISTER_COMMAND(char* commandName, func handler, BOOL restricted)` — Source: fivem/ext/native-decls/RegisterCommand.md:2,5,8.
- A registered command can be run from: the client console (client- or server-registered commands), the server console/an RCON client (server-registered commands only), or from a supported chat resource by prefixing with `/` — Source: fivem/ext/native-decls/RegisterCommand.md:11.
- The `restricted` bool is meaningless on the client — permission checks only happen server-side, so ACE-restricted commands must be registered in a server script — Source: fivem/ext/native-decls/RegisterCommand.md:15.
- When `restricted` is `true` on a server command, callers need the `command.<commandName>` ACE object allowed — Source: fivem/ext/native-decls/RegisterCommand.md:25.
- A command's handler receives `(source, args, rawCommand)`; `source` is `0` (or not `> 0`) when the command was invoked from the server console, RCON, or another resource rather than a connected player — Source: fivem/ext/native-decls/RegisterCommand.md:32-48.
- Commands registered via `RegisterCommand` can also be invoked programmatically with `ExecuteCommand` — Source: fivem/ext/native-decls/RegisterCommand.md:13.
- `ExecuteCommand(commandString)` is `apiset: shared`, `void EXECUTE_COMMAND(char* commandString)` — Source: fivem/ext/native-decls/ExecuteCommand.md:2,5,8.
- The `ExecuteCommand` doc itself states you may need `add_acl resource.<your_resource_name> command.<command_name> allow` to use it — note the doc text says `add_acl`, but the only console command actually registered in source is `add_ace` (see Section 15) — Source: fivem/ext/native-decls/ExecuteCommand.md:11.
- `RegisterKeyMapping(commandString, description, defaultMapper, defaultParameter)` is `apiset: client` only; `void REGISTER_KEY_MAPPING(char* commandString, char* description, char* defaultMapper, char* defaultParameter)` — Source: fivem/ext/native-decls/RegisterKeyMapping.md:3,8,17-21.
- The documented `+cmd`/`-cmd` convention: register two separate commands, e.g. `RegisterCommand('+handsup', ...)` (fires on key-down) and `RegisterCommand('-handsup', ...)` (fires on key-up), then map only the `+` variant with `RegisterKeyMapping('+handsup', 'Hands Up', 'keyboard', 'i')` — Source: fivem/ext/native-decls/RegisterKeyMapping.md:35-42.
- Prefixing the mapped command string with `~!` registers an alternate binding for the same logical command, e.g. `RegisterKeyMapping('~!+handsup', ..., 'o')` — Source: fivem/ext/native-decls/RegisterKeyMapping.md:15,45.
- `IsPlayerAceAllowed(playerSrc, object)` is `apiset: server`, `BOOL IS_PLAYER_ACE_ALLOWED(char* playerSrc, char* object)` — Source: fivem/ext/native-decls/IsPlayerAceAllowed.md:3,5,8.
- The ACE system is driven by four server console commands with this exact syntax: `add_ace [principal] [object] [allow|deny]`, `add_principal [child_principal] [parent_principal]`, `remove_ace [principal] [object] [allow|deny]`, `remove_principal [child_principal] [parent_principal]`, plus `test_ace [principal] [object]` to check effective access — Source: fivem-docs/server-manual/server-commands.md:646-690.
- Example ACE usage from the docs: `add_ace group.admin command.potato allow`, `add_ace identifier.steam:110000112345678 command.apple deny`, `add_principal identifier.steam:110000112345678 group.admin` — Source: fivem-docs/server-manual/server-commands.md:652-664.
- In engine source, these are registered as literal `ConsoleCommand`s named `"add_ace"`, `"add_principal"`, `"remove_ace"`, `"remove_principal"` (all compiled only under `#ifdef IS_FXSERVER`, i.e. server builds only), plus `"test_ace"` and `"list_principals"` which are compiled unconditionally — Source: fivem/code/client/citicore/se/Security.cpp:312-351,353-356,358-396,398-401,404-410,412-414.
- `add_ace`/`remove_ace` refuse to modify the ACL for the principal that is currently executing the command ("Changing ones own access is not permitted.") — checked by walking the current principal stack for a match — Source: fivem/code/client/citicore/se/Security.cpp:331-348,376-393.
- `TriggerServerEvent` vs. commands (inferred, no single doc states this directly): a command is independently invokable from the server console/RCON/chat and gets `restricted`-flag ACE enforcement for free via `RegisterCommand`'s third argument, whereas an event triggered with `TriggerServerEvent` only fires from a connected client's own script and any permission check must be written by hand inside the handler — Source: fivem/ext/native-decls/RegisterCommand.md:8-25 (inferred).

## 13. JS/TS runtime specifics

- `setTick(callback)` registers a per-tick callback with no built-in interval (runs every resource tick, like a non-yielding loop); if the callback returns a `Promise`, the scheduler skips re-invoking it until that promise settles — Source: fivem/data/shared/citizen/scripting/v8/timer.js:61-76,184-203

## 15. Gotchas

- Vectors (`vector2/3/4`, `quat`) survive event payloads and state bags: the Lua runtime's msgpack is the citizenfx/lua-cmsgpack fork (branch `grit`, pinned by `fivem/.gitmodules:161-164`, submodule not checked out here), whose `src/lua_cmsgpack.h:333-336` defines msgpack extension types 20/21/22/23 for vector2/vector3/vector4/quat and `src/pack_template_ext.h` packs them; JS receives them as arrays. Only `json.encode` lacks vector support — Source: fivem/.gitmodules:161-164; https://github.com/citizenfx/lua-cmsgpack/blob/grit/src/pack_template_ext.h (verified 2026-09-11)

**Scheduler, coroutines & events**
- Reading `source` after a `Wait()`/`Await()` inside an event handler is unreliable: the dispatcher (`Citizen.SetEventRoutine`) starts each handler in its own `Citizen.CreateThreadNow` coroutine and then unconditionally resets `_G.source = lastSource` right after starting it, without waiting for the handler to finish — if the handler then yields on `Wait`, `_G.source` has already been reset (and may be further mutated by other events dispatched while the coroutine is suspended) by the time it resumes; capture `source` into a local variable at the top of the handler before waiting on anything — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:125-179.
- The JS event dispatcher has the same class of issue in the other direction: it never restores a previous `global.source` after a nested `TriggerEvent`/`emit` call — it unconditionally sets `global.source = null` at the end of every dispatch, so a handler that calls `emit`/`TriggerEvent` synchronously will see `global.source` become `null` once that inner call returns, not the outer handler's original source — Source: fivem/data/shared/citizen/scripting/v8/main.js:486,539.
- `Citizen.CreateThreadNow` (used internally for both event dispatch and function-reference calls) runs synchronously up to the callee's first `Wait`/`Await` — this is why `TriggerEvent`/export calls "feel" synchronous in simple cases but stop being so the moment a handler waits on anything — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:171-173,482-485.
- A misspelled/nonexistent global (typo'd native, missing export-backing function, etc.) does not error where referenced — Lua's `_G.__index` returns `nil` silently (caching the miss); the script only breaks later, when it tries to *call* that `nil` — Source: fivem/data/shared/citizen/scripting/lua/natives_loader.lua:74-98.
- Passing a Lua `0` or `nil` where a native expects a *string* parameter silently becomes `nil`, not the string `"0"` — a deliberate workaround baked into the native-argument marshalling helper `_ts` — Source: fivem/data/shared/citizen/scripting/lua/natives_loader.lua:19-24.
- Native parameters typed `Hash` accept a plain Lua *string* directly — the codegen'd wrapper's `_ch()` helper auto-converts any string argument via `GetHashKey()` before invoking the native; this coercion is Lua-specific machinery, not a property of the native itself — Source: fivem/data/shared/citizen/scripting/lua/natives_loader.lua:29-35.
- Calling a non-existent Lua export raises an error immediately (`'No such export ...'`); calling a non-existent JS export throws a differently-worded error from a `Proxy` trap — neither runtime returns `nil`/`undefined` for a missing export — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:707-714; fivem/data/shared/citizen/scripting/v8/main.js:587-594.
- Both runtimes hardcode one special case: any export lookup against a resource literally named `txAdmin` is silently redirected to a resource named `monitor` instead — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:627-631; fivem/data/shared/citizen/scripting/v8/main.js:548-552.
- `exports('name', fn)` enforces exactly two arguments in JS (throws otherwise); the Lua equivalent performs no arity check at all — Source: fivem/data/shared/citizen/scripting/v8/main.js:612-622 vs fivem/data/shared/citizen/scripting/lua/scheduler.lua:732-736.

**Vectors, hashing & serialization**
- `vector2`/`vector3`/`vector4` are genuine first-class Lua types (`type(vector3(1,2,3)) == 'vector3'`), not plain tables — they support `+ - * /` (vector-vector and vector-scalar), unary negation, equality, arbitrary field swizzling, and `#v` for the Pythagorean magnitude — so `#(a - b)` is the idiomatic distance-between-two-points expression (component subtraction via `-`, then magnitude via `#`) — Source: fivem-docs/scripting-reference/runtimes/lua/functions/vector3.md:46-79.
- The bundled `json.lua` encoder has no vector-aware branch at all (confirmed by reading the whole file) — `json.encode()` on a vector value is unsupported territory: since vectors aren't plain tables, expect it to error or misbehave rather than silently produce something reasonable — Source: fivem/data/shared/citizen/scripting/lua/json.lua (absence, full read); exact failure behavior UNVERIFIED beyond "no special-case code exists".
- Event/export payloads are msgpack, not JSON: functions become funcref-proxy ext types, `Entity`/`Player` values are packed as their network-id/server-id ext types (not raw table dumps) — this is why entity/player handles (not just plain data) survive as `TriggerEvent`/export arguments across resources — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:537-624,813-943.

**Lua standard-library availability**
- Client-side Lua scripts get **no** `io` or `os` standard library at all — the runtime's library table is explicitly "a luaL_openlibs version without io/os libs" and only adds custom `io`/`os` shims (`fx::lua_fx_openio`/`fx::lua_fx_openos`) on **server** builds (`#ifdef IS_FXSERVER`) — don't assume `os.time()`/`os.date()`/`io.*` are available client-side, and don't assume the server versions behave like stock Lua's (they're custom, permission-aware implementations, evidenced by their dependency on `FilesystemPermissions.h`) — Source: fivem/code/components/citizen-scripting-lua/src/LuaScriptRuntime.cpp:162-176; fivem/code/components/citizen-scripting-lua/src/LuaOS.cpp:1-10,610.
- Prefer the documented, always-available `GetGameTimer()` native (returns milliseconds, monotonic) over `os.time()` for elapsed-time logic in code shared between client and server, given the io/os availability gap above — Source: fivem/ext/native-decls/GetGameTimer.md:8-11.
- The manifest-parsing Lua state (a *different*, throwaway state from your actual scripts) is even more restricted: no `io`/`os` at all, and `dofile`/`load`/`loadfile` are removed before your `fxmanifest.lua` runs — don't expect dynamic code loading or filesystem tricks inside a manifest — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:19-30,222-229.

**State bags & networking**
- `sv_stateBagStrictMode true` doesn't add a permission check on top of the existing path — it makes the server's legacy client-write state-bag packet handlers (both wire-format versions) complete no-ops, so any resource relying on clients writing their own `player:`/`entity:` state directly silently stops working unless the write goes through a server-authoritative event instead — Source: fivem/code/components/citizen-server-impl/src/packethandlers/StateBagPacketHandler.cpp:18-21,184-187.
- Mutating a nested field of a table already stored in state (`Entity(x).state.tbl.field = 1`) never replicates — only a direct top-level `state.key = v` (or `:set`) re-serializes and syncs the whole value; state getters/setters are shallow — Source: fivem-docs/scripting-manual/networking/state-bags.md:14-29.
- Direct field assignment on an `Entity(e)`/`Player(id)` wrapper (as opposed to `.state`) is not silently ignored — it throws a Lua error — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:865-867,904-906.
- `LocalPlayer` is simply undefined (not an error stub) in server scripts, since its assignment is skipped entirely server-side — code shared between client/server contexts must guard for this — Source: fivem/data/shared/citizen/scripting/lua/scheduler.lua:945-946.
- Exceeding the plain (non-flood, non-size) net-event or state-bag rate limit doesn't disconnect the client or error on the sender's side — the packet is just dropped server-side, at most logged once per ~15s — a resource can silently lose events/state updates under load with no client-visible error — Source: fivem/code/components/citizen-server-impl/src/packethandlers/ServerEventPacketHandler.cpp:34-42; fivem/code/components/citizen-server-impl/src/packethandlers/StateBagPacketHandler.cpp:67-113.
- Latent/reassembled events run on their own, tighter rate budget (75/s burst 125) entirely separate from ordinary `netEvent` limits (50/s burst 200) — a resource mixing both trigger styles is governed by two independent budgets — Source: fivem/code/components/citizen-server-impl/src/packethandlers/ReassembledEventPacketHandler.cpp:58-61; fivem/code/components/citizen-server-impl/src/packethandlers/ServerEventPacketHandler.cpp:23-24.
- Only `entity:`-prefixed state bags are ever auto-created on a client write to a not-yet-registered bag id; a write to a nonexistent `player:`/`global` bag is just dropped — Source: fivem/code/components/citizen-server-impl/src/packethandlers/StateBagPacketHandler.cpp:154-177.
- `RemoveStateBagChangeHandler` is explicitly marked **Experimental — may be altered or removed without warning** in its own native doc — depend on it cautiously — Source: fivem/ext/native-decls/RemoveStateBagChangeHandler.md:11.

**OneSync & entities**
- `CreatePed` called from a **server** script actually creates the ped **server-side**, despite being declared as a client-dispatched (`entity_rpc`) native and despite its own native-decl doc implying client dispatch; `CreateVehicle` under the same conditions genuinely is dispatched to run on a client. Don't assume everything in `rpc_spec_natives.lua` always executes on a client — Source: fivem-docs/scripting-reference/onesync/_index.md:156-158,172-175.
- All RPC natives (Section 7) are fire-and-forget from the calling script's perspective and are explicitly documented as fallible / not guaranteed to actually execute on the target client — don't assume a `SetEntityCoords`-style RPC native took effect without a follow-up read-back — Source: fivem-docs/scripting-reference/onesync/_index.md:169.
- `SetEntityDistanceCullingRadius`/`SetPlayerCullingRadius` are explicitly documented as deprecated with "known, unfixable issues" — treat them as best-effort bandwidth tuning, not something to depend on for correctness — Source: fivem/ext/native-decls/SetEntityDistanceCullingRadius.md:14.
- `SetRoutingBucketEntityLockdownMode` silently no-ops on an unrecognized mode string (no error, no log — there's no `else` branch) — a typo like `"stict"` fails silently; and the valid 4th lockdown-mode string is inconsistent across sources in this checkout (`no_dummy` in the C++ vs `full` in the OneSync manual) — verify against your actual server build before relying on it — Source: fivem/code/components/citizen-server-impl/src/state/ServerGameState_Scripting.cpp:560-589.
- `SetEntityOrphanMode(entity, 2)` ("KeepEntity") only stops the **server** from culling the entity on relevancy checks — a client can still explicitly delete it. Not a true persistence guarantee — Source: fivem/ext/native-decls/SetEntityOrphanMode.md:30.

**Resource manifest & fx_version**
- `lua54 'yes'` is a complete no-op on current FXServer builds — Lua 5.3 support was fully removed (client and server) as of June 2025, so every script now runs on 5.4 regardless of this key. Don't spend guide space telling readers to set it — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:299-305.
- The flag that actually gates the fast native-call path is a synthetic, unsettable metadata key `is_cfxv2`, injected only when the manifest file is literally named `fxmanifest.lua` (not `__resource.lua`) — it does **not** depend on the declared `fx_version` tier at all — Source: fivem/code/components/citizen-resources-metadata-lua/src/LuaMetaDataLoader.cpp:266-269.
- `use_experimental_fxv2_oal 'yes'` silently breaks `vector3` auto-unpacking — a native call like `SetEntityCoords(ped, coords)` must become `SetEntityCoords(ped, coords.x, coords.y, coords.z)` once OAL is enabled, or it passes garbage — Source: fivem-docs/scripting-reference/resource-manifest/_index.md:343-352.
- Raising `fx_version` to `bodacious` or later silently removes the JS `window === global` alias that earlier tiers provide for compatibility — any script relying on a bare `window.foo` breaks with no error at parse time — Source: fivem/code/components/citizen-scripting-v8/src/V8ScriptRuntime.cpp:1839-1843.
- Raising `fx_version` to `cerulean` or later switches NUI page URLs from `nui://` to `https://cfx-nui-<resource>/` — any hardcoded `fetch('http://resourcename/cb')` NUI callback URL from an older resource silently stops working once the manifest crosses this tier — check NUI callback URLs when bumping `fx_version` — Source: fivem/code/components/nui-resources/src/ResourceUI.cpp:71-72.
- A resource below `fx_version 'adamant'` (or with no recognized `fx_version` at all) is refused at server start, not just warned about — Source: fivem/code/components/citizen-server-impl/src/ServerResources.cpp:536-540.

**Commands, ACE & convars**
- `RegisterCommand`'s `restricted` flag is meaningless on the client — there is no client-side permission system, so ACE enforcement for a command only happens if it's registered in a **server** script — Source: fivem/ext/native-decls/RegisterCommand.md:15.
- Standard (`set`) convars are invisible to client scripts entirely — only `SetConvarReplicated` (`setr`) or `SetConvarServerInfo` (`sets`) values ever reach the client. A common bug is calling plain `SetConvar` and then wondering why `GetConvar` returns the default on the client — Source: fivem-docs/scripting-reference/convars/_index.md:60,64,83-84.
- Neither `add_ace`/`remove_ace` nor `add_principal`/`remove_principal` let the currently-executing principal modify its own ACL entry — a self-service "promote me to admin" script fails silently with "Changing ones own access is not permitted." — Source: fivem/code/client/citicore/se/Security.cpp:331-348,376-393.
- The `ExecuteCommand` native's own doc page says `add_acl` where every other doc and the actual console-command registration say `add_ace` — a likely stale typo; don't copy `add_acl` into a server.cfg — Source: fivem/ext/native-decls/ExecuteCommand.md:11 vs fivem/code/client/citicore/se/Security.cpp:313.
- `sv_licenseKey` is stored and readable as a plain string convar — a resource that dumps/logs all convars for debugging can leak it; treat it as a secret — Source: fivem-docs/server-manual/server-commands.md:264-266.

**JS/TS runtime**
- Calling a CitizenFX **server** native from inside a Node.js-native callback (e.g. `fs.readFile`'s callback) fails with `"No current resource manager"` because natives may only run on the main game thread — hop back with `setImmediate(() => { /* natives here */ })` — Source: fivem-docs/scripting-manual/runtimes/javascript.md:110-138.
- `setImmediate(fn)` in the JS runtime is **not** a true "next microtask" — it's implemented as `setTimeout(fn, 0)` under the hood, still subject to the normal timer pass — Source: fivem/data/shared/citizen/scripting/v8/timer.js:156-162.
- KVP natives are `apiset: shared` — readable/writable from **client** scripts too, each side with its own independent per-resource store — easy to wrongly assume KVPs are server-only — Source: fivem/ext/native-decls/kvp/SetResourceKvp.md:3.
- Forgetting to invoke a registered NUI callback's `cb()` hangs the browser-side `fetch()` in the UI until it times out; the capitalized Lua-global `RegisterNUICallback` is documented as legacy — new code should call the native directly — Source: fivem-docs/scripting-manual/nui-development/nui-callbacks.md:97-98; fivem-docs/scripting-reference/runtimes/lua/functions/RegisterNUICallback.md:5-7.
- `PerformHttpRequestAwait` silently requires server build 9515+ — using it against an older FXServer artifact is a portability footgun not obvious from the Lua syntax alone — Source: fivem-docs/scripting-reference/runtimes/lua/functions/PerformHttpRequestAwait.md:5.

**Events & documentation gaps**
- Not every event scripts commonly rely on is documented on docs.fivem.net's events list — `weaponDamageEvent`, `explosionEvent`, `fireEvent`, `ptFxEvent`, `startProjectileEvent`, `giveWeaponEvent`, `removeWeaponEvent`, `removeAllWeaponsEvent`, `clearPedTasksEvent`, and `playerJoining` only have their canonical documentation as `/*NETEV*/`-style comments in the C++ source — treat this fact sheet's Section 9 as more authoritative than the docs site for these — Source: fivem/code/components/citizen-server-impl/src/state/ServerGameState.cpp:4927; fivem/code/components/citizen-server-impl/src/ClientRegistry.cpp:196.
- `entityCreating` (synchronous `TriggerEvent2`, cancel removes the just-created clone) vs `entityCreated` (fire-and-forget `QueueEvent2`, cancel has no effect) is the concrete case of a general rule: to veto something, hook the `...ing`/pre-action event, not the `...ed`/post-action one — Source: fivem/code/components/citizen-server-impl/src/state/ServerGameState.cpp:3670-3678,3685-3693.
- `playerConnecting`'s non-deferred cancellation path (`CancelEvent()` + `setKickReason(...)`) cannot `Wait()` or do async work at all; any I/O-bound check (ban list, whitelist DB, etc.) must use `deferrals`, and must wait at least one tick after `defer()` before calling `update`/`presentCard`/`done` — calling `deferrals.done()` on the same tick as `defer()` is a common footgun — Source: fivem-docs/scripting-reference/events/list/playerConnecting.md:29-30,45-46,132-154.
- `onResourceStart`/`onResourceStop`/`onClientResourceStart`/`onClientResourceStop` fire globally for **every** resource's start/stop, not just your own — every official example guards with `if GetCurrentResourceName() ~= resourceName then return end` — Source: fivem-docs/scripting-reference/events/list/onResourceStart.md:22-27.
- `rconCommand` is explicitly deprecated in favor of `RegisterCommand(..., restricted)` — Source: fivem-docs/scripting-reference/events/list/rconCommand.md:8-10.

**Debugging & ops**
- RCon's transport is a raw, plaintext, non-constant-time-compared UDP protocol rate-limited only at 0.2 req/s (burst 5) per source address — treat `rcon_password` like any other secret and put the RCon port behind a firewall/allowlist, since the protocol itself adds little hardening — Source: fivem/code/components/citizen-server-impl/include/outofbandhandlers/RconOutOfBand.h:22-51.
- An empty `rcon_password` doesn't just mean "weak password" — it fully disables RCon (every request gets a "must set rcon_password" reply), a secure-by-default behavior worth relying on rather than fighting — Source: fivem/code/components/citizen-server-impl/include/outofbandhandlers/RconOutOfBand.h:40-45.
- `resmon`/`strdbg` (and other dev-only console commands) silently return "Access denied" unless the client was launched with `+set moo 31337` — don't assume `resmon` output is available on a tester's machine — Source: fivem-docs/client-manual/console-commands.md:133; fivem-docs/scripting-manual/introduction/fact-sheet.md:61.
- `ensure` (start-if-stopped, restart-if-running) is the safe default for iterating on a resource; `refresh` is required first whenever a resource is newly added to disk, since manifests are only rescanned on `refresh`, not automatically — Source: fivem-docs/server-manual/server-commands.md:33-57.
- Familiar-feeling admin commands like `status`, `clientkick`, and `say` are not part of the FXServer engine at all — they come from the default `rconlog`/`chat` resources, so a from-scratch server config won't have them until those resources are included — Source: fivem-docs/server-manual/server-commands.md:91-117.
- The server-side profiler view link embeds a `token` query parameter sourced from the server's profile-data token whenever one is set — treat it like a credential rather than a throwaway debug URL — Source: fivem/code/components/citizen-server-impl/src/InfoHttpHandler.cpp:487-495 (inferred purpose of the token from its usage as a query auth parameter).
